# A COPY of /requirements-cloud.txt, kept here too because @vercel/python's builder looks
# for requirements.txt next to the entrypoint (api/index.py) rather than at the project
# root. Keep the two files identical by hand - /requirements-cloud.txt is the source of
# truth and is what a human should edit; this copy is what the build actually reads.
#
# Dependencies for a Vercel (RAG_MODE=cloud) deployment. This is requirements.txt minus
# torch and sentence-transformers, which do not fit a serverless bundle and are unused in
# cloud mode anyway (embeddings and re-ranking are HTTP calls - see EMBEDDINGS_PROVIDER /
# RERANKER_PROVIDER in src/core/config.py). Everything else is unchanged; the app code is
# identical between local and cloud, only which packages back each piece differs.
#
# rank-bm25 stays: BM25 runs per-user, in memory, even in cloud mode (see services/bm25.py)
# - it is a pure-Python, no-torch dependency, so there is nothing to trim there.
#
# Keep this in sync with requirements.txt by hand. There is deliberately no shared base
# file with an exclusion list - Vercel's build reads this file directly, and a hidden
# extra layer of indirection is exactly what this project's "no hidden abstractions" rule
# argues against.
#
# ONE deliberate divergence from requirements-cloud.txt: chromadb is dropped here. It
# pulls onnxruntime, a kubernetes client, grpcio and opentelemetry exporters as transitive
# deps (~250MB), which pushed the Vercel function bundle over its 225MB cap. vectorstore.py
# imports the chroma backend lazily (services/vector_chroma.py), only when VECTOR_STORE=
# chroma - and cloud mode's default is VECTOR_STORE=pinecone, so it is never imported in a
# default Vercel deployment. If you deploy to Vercel with VECTOR_STORE=chroma (Chroma
# Cloud), add chromadb back here.
